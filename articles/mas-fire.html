AIエージェントAI評価信頼性

壊して初めて分かるエージェントの弱点——MAS-FIREで「失敗後の回復」を評価する

MAS-FIRE: Fault Injection and Reliability Evaluation for LLM-Based Multi-Agent Systems

Jin Jia / Zhiling Deng / Zhuangbin Chen / Yingqi Wang / Zibin Zheng · 2026
公開 2026.09.13　／　推定読了 57分

AIエージェントが通常条件で80%成功したとしても、「途中のagentが間違った要約を渡した」「tool parameterが少し壊れた」「同じmessageが何度も届いた」ときにどう振る舞うかは分からない。MAS-FIREは、multi-agent systemへ故障を意図的に注入し、最終成功率だけでなく、異常を検知したか、局所的に直したか、その修復が最終成功まで届いたかを分けて測る。

LLM agentの故障は、例外を投げずに進む

従来のdistributed systemでは、service crash、timeout、network partitionのようなfailureを扱う。故障はruntime上のeventとして観測しやすく、retryやfailoverのtriggerも設計しやすい。

LLM-based multi-agent systemでは別の故障が増える。plannerが存在しないtoolを計画に入れる。memory圧縮で重要constraintを落とす。agent Aのhallucinationをagent Bが正しい前提として採用する。役割定義が曖昧で、同じ仕事を二人が別解釈する。messageが重複しても、system自体は停止しない。

つまり「動いているが意味が壊れている」という状態が起こる。通常のexception monitorでは拾えないため、end-to-endのtask successだけ見ても、どこで壊れたか分からない。

MAS-FIREの出発点は、agentic systemのreliabilityをこのsemantic faultまで含めて評価することである。

fault injectionを、AIエージェントへ持ち込む

fault injectionはreliability engineeringで古くから使われる。正常なsystemへ意図的に異常を起こし、failure detection、containment、recoveryが期待どおり働くかを見る。rare failureを本番で待つ代わりに、test環境で強制的に再現する。

MAS-FIREはこの考えをLLM agentへ移植する。ただしcodeを直接改変するのではなく、agent architectureの外側からfaultを入れる。著者らは三つのinject mechanismを用意する。

Prompt modification

role定義やuser instructionを変え、曖昧さや論理矛盾を注入する。

Response rewriting

agent出力を途中で捕まえ、hallucination、情報欠落、tool parameter errorなどへ書き換える。

Message routing

messageの重複、cycle、誤broadcastなど、communication flowそのものを変える。

このnon-invasiveな設計が重要である。system本体へ専用の故障コードを書き込まず、middleware的に故障を注入するため、異なるmulti-agent frameworkを同じ観点で比較できる。

15種類のfaultを、「agent内部」と「agent間」に分ける

MAS-FIREはfaultをまずintra-agentとinter-agentへ分ける。intra-agentは一つのagent内部で起きるplanning、memory、reasoning、actionの失敗である。inter-agentはconfiguration、instruction、communicationの失敗で、agent間の依存関係やmessage flowから生じる。

planning faultには、実行不能planやcritical information lossがある。memory faultにはconversation historyの喪失やcontext length violationがある。reasoning faultでは、検証済み事実をもっともらしい誤情報へ差し替えるhallucinationを注入する。action faultではtool selection、parameter filling、parameter formatを壊す。

inter-agent側では、role ambiguityやblind trust、instruction logic conflict、instruction ambiguity、message cycle、message storm、broadcast amplificationなどを扱う。

ここで効いているのは、単なる「難しいpromptを投げる」benchmarkではないことだ。どの機能層へどの故障を入れたかを固定し、その後のsystem responseを観察できる。

原文外の補助例

複数人で旅行計画を作るとする。幹事が日付を一日間違えて伝えた場合と、予約担当がホテル名を取り違えた場合と、同じ連絡が20回届いた場合では、必要な回復行動が違う。「旅行が成立したか」だけでは、チームのどこが強かったか分からない。故障を種類別に入れると、確認、再質問、重複除去、再予約などの回復能力を分けて見られる。

最終成功率の前に、「気づいたか」を測る

MAS-FIREはsystem-levelのRobustness Scoreだけでなく、process-level metricを置く。ここがこの論文の使いやすい部分である。

Occurrence Rateは、faultに対して何らかのfault-tolerant behaviorがtriggerされた割合を見る。異常を認識せず、そのまま下流へ流した場合は低くなる。

Local Success Rateは、triggerした回復行動が注入faultを局所的に直せたかを見る。tool parameter errorを検知して正しいparameterへ修正できたならlocal successである。

Success Rateは、その局所修復のあと最終taskまで成功したかを見る。途中を直しても、既に誤情報が別agentへ伝播していればend-to-endでは失敗することがある。

この三段階を分けると、「気づかない」「気づくが直せない」「直すが手遅れ」という異なるfailure modeが見える。

局所修復と全体成功の差が、cascadeを見せる

multi-agent systemでは、faultが一つのagentに閉じない。agent Aの誤ったsummaryがshared memoryへ入り、agent BとCがそれを前提に別作業を進めれば、Aを後から修正しても全体状態は戻らない。

このためLocal Success Rateとfinal Success Rateのgapが重要になる。局所エラーを直せるのに最終成功へ戻れないsystemは、recovery mechanismが弱いというより、fault propagationをcontainできていない。

設計上は、shared stateのversioning、再検証trigger、dependency-aware rollback、downstream notificationなどが候補になる。論文そのものがこれらすべてを実装するわけではないが、どの対策が必要かをprocess traceから切り分けられる。

「賢いmodelなら丈夫」は成立しない

著者らはMetaGPT、Table-Critic、CAMELという異なるarchitectureを、GPT-5とDeepSeek-V3系modelで評価する。結果は、foundation modelが強くなればreliabilityが一様に上がるという単純なものではない。

強いmodelはsemantic reasoningが必要なfaultへ対応しやすい一方、instruction corruptionに対しては与えられた指示へ忠実すぎることで逆に脆くなる場合がある。矛盾したconstraintを明示的に拒否せず、両方満たそうとして壊れる、といった現象である。

reliabilityはmodel capabilityだけでなく、architecture、validation rule、shared state、communication patternの組合せで決まる。これはagent systemを「LLMの性能を外側から呼び出すだけ」と見る設計を崩す。

closed-loop architectureは、faultを吸収しやすい

論文で大きな差が出たのがarchitecture topologyである。iterativeなcritic-refinerやclosed-loop構造は、linear workflowでcatastrophic failureになるfaultの40%以上をneutralizeしたと報告される。

linear workflowでは、上流の誤りが承認されないまま次へ進む。一方、criticやjudgeが戻り経路を持つsystemは、後段で矛盾を発見して前段へ修正要求を返せる。

ただし「loopを増やせばよい」わけではない。loop自身がmessage cycleや無限retryを生む可能性もある。重要なのは、どの異常で再確認し、何回まで戻し、どの状態を再検証するかを設計することになる。

blind trustは、multi-agent化の副作用である

multi-agent systemは役割分担をするため、agent同士が他者の出力をinputとして受け取る。ここで「専門agentが出したから正しい」というimplicit trustが生まれる。

MAS-FIREのblind trust faultは、この前提を意図的に強め、上流errorがどこまで伝播するかを見る。これは実運用でも現実的な問題である。retrieval agentの引用、plannerのsubtask、review agentの判定を、下流が無条件に採用すれば、一つの誤りがsystem全体の確信へ変換される。

対策はagentを増やすことではなく、どのhandoffでverificationが必要かを決めることになる。authorityを分けるなら、同時にverification responsibilityも分けなければならない。

要求の曖昧さも「system fault」としてテストできる

MAS-FIREはuser instruction側のlogic conflictとambiguityもfaultとして扱う。これは重要で、agent評価を「正しい仕様が与えられた前提」から外へ広げる。

現実の依頼は、constraintが衝突したり、語が曖昧だったりする。そこでsystemが勝手に一方を選ぶのか、clarificationを返すのか、矛盾を明示するのかでreliabilityが変わる。

つまり要求品質の問題を、入力側の不備として評価対象外にせず、agent systemの応答能力として測れる。これは要求工学とagent評価の接点になる。

既収録の「成功率では足りない」を、故障実験へ進める

既収録の「Towards a Science of AI Agent Reliability」は、consistency、robustness、predictability、safetyを12 metricへ分けた。τ-benchは同じtaskを反復してpass^kで安定性を見る。Metamorphic Testingは正解oracleが作りにくいとき、入力変換と出力関係をテストする。

MAS-FIREの差分は、失敗を待たずに作ることである。特定faultを注入し、systemの検知・修復・回復をprocess traceとして見る。reliability評価を観察から介入へ進める。

agent evaluationを「正常時」と「故障時」の二層に分ける

実務で使うなら、通常task benchmarkとfault-injection benchmarkを分けるとよい。通常taskではcapabilityとbaseline successを測る。故障時ではbaselineで成功したtaskだけを対象に、特定faultを注入してどれだけ成功を維持できるかを見る。

こうすれば「元から難しくて失敗したtask」と「本来成功できるのにfaultで壊れたtask」を混同しない。さらにfault type別のprofileを作れば、tool errorには強いがinstruction ambiguityには弱い、といったsystem特性が見える。

aggregate score一つに潰さず、fault taxonomyごとのheatmapを持つ方が改善へつながる。実際の対策はfaultごとに違うからである。

限界——注入したfaultが現実のfailure分布を代表するとは限らない

fault injectionには常にrepresentativenessの問題がある。15 faultはliterature review等を基に整理されているが、実際のproduction incidentの頻度や組合せを完全には表さない。

また、LLMを使ってsemantic mutationを作る部分はinjector model依存である。同じ「hallucination」でも難易度が違えばsystem responseは変わる。fault intensityの校正も今後の課題になる。

multi-agent architectureも三種類に限られ、task domainやtool environmentが変われば結果は変わる。したがって「closed-loopなら常に40%強い」と一般化するより、architecture topologyがreliabilityに大きく効くという方向を持ち帰る方が安全である。

実務へ持ち帰るなら

  1. agentのfailure logをplanning・memory・reasoning・action・coordinationへ分類する。
  2. 本番で起きたfaultを再現できるinjection harnessを作る。
  3. 最終successだけでなく、検知、局所修復、最終回復を別metricにする。
  4. 上流agent出力を無条件に信頼しているhandoffを洗い出す。
  5. 曖昧・矛盾したuser instructionに対するclarification behaviorをtest caseにする。
  6. linear workflowには、どこでvalidation loopを入れるとfault propagationを止められるかを検討する。

AI agentを「賢い部品の連結」と見ると、失敗はmodel errorへ還元される。fault injectionを入れると、情報の流れ、役割、verification、recovery pathというsystem designの問題が見える。
