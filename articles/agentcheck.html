壊れたツールを「同じ壊れ方」で再現する——AgentCheckでMCPエージェントの修正を検証する

AgentCheck: A Reproduce-Intervene-Mitigate Workbench for LLM Agents over MCP

Aritra Mazumder / Nusrat jahan Lia · 2026
公開 2026.09.13　／　推定読了 54分

tool-using agentの評価は、toolが正しく返ることを暗黙に前提にしがちである。しかし本番では、timeout、古い値、schemaの崩れ、tool descriptionの汚染が起きる。AgentCheckはMCP serverを介入面として使い、実際のtool responseを記録した後、一か所だけ故障へ差し替えて同じrunを再生する。修正を入れたら同じfaultをもう一度流し、「本当にその修正で直ったか」まで比較する。

本番のagent failureは、再現できないこと自体が問題になる

普通のsoftware debuggingでは、入力と状態を固定し、同じbugを再現してから修正する。agentではこれが難しい。LLM出力が確率的で、toolがlive dataを返し、外部serviceの状態も変わるからである。

たとえば昨日だけinvoice APIがtimeoutしたとする。そのときagentは誤ったfallbackを選んだ。しかし翌日に再実行するとAPIは正常で、failure pathへ入らない。修正したretry logicが効いたのかどうかも確認しにくい。

AgentCheckが狙うのは、agentの「壊れた一回」をfixtureへ変えることだ。実toolとのclean runを記録し、faulted runでは一致するtool callをcacheからreplayする。agentが故障の影響で別経路へ分岐した後だけlive toolへ戻る。

record-replayだけではなく、一点だけ介入する

完全replayならすべてのtool responseを固定できるが、agentが違う行動へ分岐した後の世界まで再現するのは難しい。AgentCheckはそこを二段に分ける。

まずclean runでtool callとresponseを記録する。次にfault injectorが対象responseへ一つの変化を入れる。それまで同じtool callが続く間はcacheを使い、faultによってagent trajectoryがclean runと違った時点からlive executionへ切り替える。

この方式だと、故障以前の条件はほぼ固定しながら、故障後にagentが取るrecovery actionは実際に試せる。単なるsimulationより、修正の影響を現実のtool環境へ接続しやすい。

12種類のfaultは、transport errorだけではない

AgentCheckのfault catalogは、timeoutのような明示的errorだけでなく、より厄介な「成功に見える誤り」を含む。stale data、malformed response、semantic corruption、tool description poisoningなどである。

この違いは大きい。HTTP 500ならretry policyを起動しやすい。だが一週間古い在庫数が200 OKで返れば、agentは疑わず使う可能性がある。tool descriptionへ悪意あるinstructionが混ざっていても、protocol上は正常である。

著者らの実験でも、典型的failureはcrashより間違ったtool outputを自信を持って採用することだった。agent reliabilityでは「止まったか」だけでなく、「誤ったまま進んだか」を観測する必要がある。

原文外の補助例

電車の発車案内が消えていれば、利用者は駅員へ確認しやすい。表示が普通に点灯していて、時刻だけ昨日のものなら、そのまま信じてしまう。agentも同じで、明示的errorよりplausibleなstale responseの方が検知しづらい。

reproduce → intervene → confirmを一つのloopにする

AgentCheckのworkflowは三段階に整理できる。第一にfailureを再現する。第二にfaultを固定したままmitigationを入れる。第三に同じfaultで再実行し、failureが消えたかを確認する。

ここで大事なのは、「対策を実装した」ことを成功条件にしない点である。retry、schema validation、freshness check、tool allowlistなどをtoggleして、同一のfault scenarioに対する行動差を見る。

原因と修正を対応させやすくなるため、incident reviewをbenchmarkへ変換できる。本番で起きた一件を、そのままregression testへ持ち込む発想に近い。

deterministic checkとLLM judgeを分ける

scoringは二層ある。明確に機械判定できるものはdeterministic pass/fail ruleを使う。たとえば「外部domainへ送信してはいけない」「古い値を最終回答へ使ってはいけない」のような条件である。

一方、「agentが適切に不確実性を表明したか」「説明が安全だったか」のようにinterpretationが必要なlabelはLLM judgeを補助的に使う。著者らはjudge labelをhuman annotationと比較してvalidationする。

論文の限界節でも、deterministic checkとjudgeは独立したfallible signalであり、disagreementがあると明記する。primary verdictをdeterministic checkへ寄せ、judgeをdiagnosticとして扱う。これはagent evaluationの設計としてかなり堅実である。

5 agentで77/120から105/120まで差がつく

著者らは5種類のagentを120 scenarioで評価し、最良agentが105、最弱agentが77 scenarioをpassしたと報告する。通常taskだけでは見えにくい差が、fault conditionで広がる。

重要なのは、agentの「平均能力」よりfailure classごとのprofileである。timeoutに弱いagent、stale dataに弱いagent、poisoned descriptionに弱いagentでは対策が違う。

このためscoreを一つに潰すより、fault taxonomyごとにpass rateを持つ方がdeployment readinessを判断しやすい。

retryはtimeoutを直しても、stale dataは直さない

最弱agentへretry mitigationを入れると、timeout error faultでは成功率が30%程度から100%へ改善したcaseがある。これはretryがtransport-level failureへ効くことを示す。

しかしstale-data faultは、同じmitigationを入れても10件中3〜4件程度の成功に留まる。古い値を何度取り直しても、source側が古いなら同じものが返るからである。

この対比は実務的に重要だ。「tool failure」という大分類へ一つのfallbackを付けても、failure semanticsが違えば効かない。timeoutにはretry、stalenessにはfreshness metadataやcross-check、description poisoningにはtrust boundaryが必要になる。

MCPを「接続規格」だけでなくtest seamとして使う

MCPの価値はtool接続を標準化することだけではない。tool callとresponseがprotocol boundaryを通るため、そこへlogging、fault injection、replay、policy checkを差し込める。

AgentCheckはこの境界をintervention surfaceと呼ぶ。agent本体を書き換えずにtool responseを差し替えられるため、異なるagent implementationへ同じfaultを流せる。

これはsystem design上の示唆も持つ。外部依存との境界が明確なら、そこはobservabilityとtestingの境界にもできる。protocol designがevaluation infrastructureを兼ねる。

MAS-FIREとの違い——system全体のtaxonomyと、再現可能なdebug loop

同日に採用したMAS-FIREもfault injectionを扱う。両者は近いが、焦点が違う。MAS-FIREはplanning、memory、reasoning、action、coordinationへ15 faultを体系的に配置し、検知・局所修復・最終回復を測る。multi-agent architectureのreliability profileを作る研究である。

AgentCheckはtool boundaryへ対象を絞り、本番failureを同じ条件で再現し、mitigationの前後を比較するdeveloper workbenchに寄る。特にMCP上でrecord/replayとlive divergenceを組み合わせるところが実装上の持ち味である。

片方はfailure taxonomyとsystem比較、もう片方はreproducible debugging。両方を組み合わせれば、fault classを整理しながらincident regression testを蓄積できる。

agentの回帰テストに必要なのは「同じ質問」だけではない

LLM agentの回帰テストでは同じuser promptを再投入しがちである。しかしtool worldが毎回変われば、failureの再現条件が揃わない。

AgentCheckの示唆は、input promptだけでなくenvironmental responseもtest fixtureとして管理することだ。どのtool callまで同じresponseを返し、どのpointでfaultを入れ、どこからliveへ戻すかをversioningする。

これにより「model update後にstale-data耐性が落ちた」「新しいplannerはtimeout時のretryは増えたが二重実行も増えた」といったregressionを追える。

silent failureを観測するには、traceへ意味ラベルが要る

agentがcrashしないfailureでは、trace上のtool callは成功している。そこで「response freshness」「schema validity」「source trust」「side effect completion」のようなsemantic checkをtraceへ追加する必要がある。

単なるHTTP status、latency、token数だけでは足りない。tool outputをどの判断に使ったか、agentが疑義を示したか、別sourceへverificationしたかも見る。

AgentCheckのfaulted runとclean runのside-by-side比較は、その意味差を見つけるためのUIとして機能する。

限界——tool faultの再現は、世界全体の再現ではない

record/replayで固定できるのはMCP境界を通るresponseであり、agent内部のrandomnessや外部環境すべてを固定するわけではない。agentが早い段階でtrajectoryを変えれば、その後のlive callは前runと違う世界へ入る。

また12 faultがproduction failureの全分布を代表するとは限らない。複数faultが同時発生するcase、長期memory corruption、tool間の不整合などはさらに複雑である。

LLM judgeもground truthではない。著者ら自身がdeterministic ruleをprimaryに置いているように、解釈的評価は補助として扱う方が安全である。

実務へ持ち帰るなら

  1. production incidentで使われたtool responseを、再現可能なfixtureとして保存する。
  2. timeout、stale data、schema drift、description poisoningを別fault classとして管理する。
  3. mitigationを入れたら、同じfaultへ再度流してpass/failを比較する。
  4. deterministicに判定できるsafety・correctness条件はLLM judgeへ任せない。
  5. MCPやAPI gatewayの境界へlogging・replay・fault injectionを置く。
  6. agent regression testではpromptだけでなくtool environmentもversioningする。

agentの信頼性を上げるには、失敗を「もう起きないように祈る」のではなく、失敗を保存し、何度でも再生できるtest caseへ変える必要がある。
