RAGAI評価検索制御

「検索するか」を精度だけで評価しない——Active RAGを予算・害・閾値転移まで測る

When Should Active RAG Retrieve? A Budget-Aware Evaluation of Utility, Calibration, and Cost

Pin Qian / Su Wang / Chong Peng / Junxian You / Lifei Liu / Haoran Yu / Yihang Chen / Xiaochong Jiang · 2026
公開 2026.09.13　／　推定読了 55分

検索は無料ではない。latencyとtokenを使い、余計な資料を入れれば、もともと正しかった回答を壊すこともある。Active RAGは「必要なときだけ検索する」ための仕組みだが、その評価で単に最終accuracyだけを見ると、頻繁に検索して予算を多く使ったsystemが強く見える。Qianらは検索triggerを、utilityの順位づけ、閾値のbudget calibration、retrieval harm、意思決定自体のcostへ分けて評価する。

「検索した方がよい質問」を見つける問題

通常のRAGはqueryごとに必ずretrievalを走らせる。Active RAGやadaptive retrievalは、LLMだけで答えられそうなら検索せず、不確実なときや外部知識が必要なときだけretrievalをtriggerする。

これには二つの利点がある。第一に、検索・rerank・context processingのcostを減らせる。第二に、不要なretrieval noiseを避けられる。外部資料は常にhelpfulではなく、誤ったpassageや過剰なcontextが回答を悪化させることがある。

そのためrouterやtriggerの仕事は「難しい質問を見つける」ことではない。検索すると回答結果が改善するqueryを見つけることである。

retrieval utilityを、検索ありと検索なしの差として定義する

論文はquery iについて、検索あり回答のcorrectnessから検索なし回答のcorrectnessを引いた値をretrieval utilityとして置く。binary correctnessならutilityは+1、0、-1の三種類になる。

+1 helpful

検索なしでは誤答、検索すると正答になる。

0 neutral

検索してもしなくてもcorrectnessが変わらない。

-1 harmful

検索なしでは正答だったのに、検索後に誤答へ変わる。

この定義は「検索すべきか」を知識不足のproxyで測らず、最終的なmarginal effectで測る。LLMが不確実でも検索が役立たない質問はあるし、自信満々でも検索で救える質問もある。

retrieval harmを無視すると、routerの目的を間違える

検索は通常「役立つか、役立たないか」の二値で考えられがちだが、この論文はharmを明示する。2WikiMultiHopQAでは、検索によってもともと正しかった回答が誤りになるcaseが8.8%あったと報告される。

害の原因は一つではない。retrieverが紛らわしい資料を出す、generatorが弱いevidenceへ引っ張られる、contextが長くなって重要情報を見失う、矛盾資料の扱いを誤る、といった経路がある。

したがってrouterは「検索で改善するcase」を上位へ置くだけでなく、「検索すると壊れるcase」を下位へ置く必要がある。検索率を上げればaccuracyも上がるという単調な前提は置けない。

原文外の補助例

道に迷ったとき、毎回検索する方が良いとは限らない。すでに駅の改札前にいて案内表示が明確なのに、古いblogを検索して工事前の出口情報を読めば、かえって遠回りする。検索の価値は「情報が増えること」ではなく、検索しなかった場合と比べて判断が改善することにある。

accuracyだけ比較すると、予算が違うsystemを同列に並べてしまう

Active RAG system Aがqueryの30%だけ検索し、system Bが70%検索するとする。Bのaccuracyが高くても、その差がrouterの賢さによるのか、単に外部evidenceへ多くアクセスしたからか分からない。

論文が問題にするのがoperating pointである。同じ「50% budget」を掲げる方法でも、held-out dataで実際に50% retrievalになるとは限らない。thresholdをdevelopment setで調整し、本番分布が変われば、実現retrieval rateはずれる。

system比較では「同じbudgetで誰が良いutilityを拾えるか」と「設定したbudgetを未知dataでも守れるか」を分けなければならない。

Exact top-k frontierは、routerの純粋な順位能力を見る

第一の評価はdiagnosticなexact top-k utility frontierである。test set全体のrouter scoreを見て、budget ρに応じて上位k件だけ強制的にretrievalする。

これはdeploymentではできない。未来queryを全部並べてから上位何件かを選べないからである。しかしdiagnosisには役立つ。threshold calibrationの失敗を除き、「このscoreは本当にretrieval utilityの高いqueryを上へ並べているか」を純粋に測れる。

budgetを10%、20%、50%と動かしてcurveを見ると、router Aは低budgetで強いが高budgetではBに抜かれる、といった差も見える。単一operating pointのaccuracyより情報量が多い。

Deployable frontierは、過去で決めたthresholdが未来で守れるかを見る

本番ではcalibration setでthresholdを決め、新しいqueryへ適用する。第二のdeployable threshold frontierは、この現実的な手順でaccuracyと実現retrieval rateを測る。

ここではrouter scoreのrankingが良くても、score distributionがshiftするとbudgetを外す。developmentで「このthresholdなら50%検索」と調整しても、held-outでは65%になるかもしれない。

この差はthreshold-transfer errorとして独立に見る価値がある。systemが精度を稼いだ理由が、良いroutingか、budget overshootかを分けられるからである。

Conservative frontierは「予算超過しない」を設計要件にする

第三のconservative budget frontierは、budget超過を避けるために安全marginを置く。calibration sampleから得たretrieval rateに不確実性がある以上、targetぴったりへthresholdを置くと本番で超える可能性がある。

そこで一定のconfidenceでbudget内へ収まるよう、より厳しいthresholdを設定する。当然retrieval機会を減らすのでaccuracyを少し失うかもしれない。このtrade-offを明示する。

これはcost limitがhard requirementのsystemに重要である。「平均では安い」より「上限を超えにくい」が必要なサービスでは、accuracy最大化だけではoperating pointを決められない。

trigger自身のcostを数えないと、節約systemが高くつく

Active RAGは「検索を減らすから安い」と思いやすい。しかしretrievalするか判断するために、追加LLM call、複数sample、entropy計算、full answer生成などを使う場合がある。

たとえば「まず回答を一度生成し、そのuncertaintyが高ければretrievalして再生成する」方式なら、検索したcaseではgenerationを二度行う。routerが高性能でも、trigger-side computeが大きければtotal costは増える。

論文はcostをretrievalだけでなく、pre-decision compute、retrieval、post-decision generationへ分解する。accuracy-vs-retrieval-rateだけでなく、token-equivalent costのfrontierを見る。

複雑なrouterが単純baselineに勝つとは限らない

実験では、learned utility router、uncertainty、retrieval scoreなど複数方式を比較する。結果はdatasetとbudgetでrankingが変わり、simple uncertaintyやretrieval-score baselineが学習型routerへ並ぶ場面もある。

この結果から言えるのは、特定routerが普遍的に最善ということではない。router評価には、dataset、budget、generator、retriever、cost modelが入る。単一平均scoreでmethodを決めると、deployment条件とずれる。

特に低budget運用ならtop fewのhelpful casesを正しく拾う能力が重要で、高budgetならharmful casesを避ける能力の比重が上がる。目的関数がoperating pointで変わる。

検索停止と追加検索は、同じutility問題として考えられる

論文は「検索するかしないか」というtriggerを扱うが、考え方はmulti-step RAGの停止条件にも広げられる。今のEvidence Setに対して、もう一回検索するmarginal utilityが正なら続け、0付近なら止め、negativeならむしろ害になる。

重要なのは「まだ検索できるか」ではなく、「追加検索が現在の回答状態をどれだけ変える見込みがあるか」である。取得件数やround数はbudget constraintであってutilityではない。

MAP-Lawのcoverage-driven retrievalと組み合わせるなら、未解決要件があることをgap signalとし、そのgapを埋める検索のexpected utilityとcostを見てcontinue/stopを決める、という構造にできる。

「不確実だから検索」は一段粗い

uncertaintyは便利なtriggerである。しかしuncertaintyが高いことと、retrievalで改善できることは同じではない。知識がなくて不確実なのか、推論が難しいのか、質問自体が曖昧なのかで対策が違う。

曖昧queryなら検索よりclarificationが有効かもしれない。推論errorならより多くのdocumentを足しても改善しない。既に正しいが自信が低いcaseでは検索costだけ増える。

したがってrouterのtargetを「uncertainか」から「retrieval interventionのutilityが正か」へ変えると、検索制御の目的が明確になる。

既存記事との差分

MAP-Lawは法的要件のcoverageと未解決gapから次検索を制御する。ARKはanswer-centricなretriever trainingを扱う。Evidence-aware retrieval utilityの記事は、retrieval評価signalが下流意思決定へ本当に効くかを検証する。

本稿の焦点は、検索行為そのものをbudgeted interventionとして評価することにある。いつ検索するか、何%検索するか、thresholdが未知dataで予算を守るか、検索が害になるcaseをどれだけ避けるか、判断costまで含めて見る。

評価表に最低限入れたい六項目

Active RAGや検索停止の検証をするなら、final accuracyだけでなく次の項目を並べるとよい。

  1. retrieval usage rate——実際に何%のqueryで検索したか。
  2. utility ranking——helpful queryを上位に並べられたか。
  3. harm rate——検索で正答から誤答へ落ちた割合。
  4. threshold-transfer error——calibration時の想定budgetとheld-out実績の差。
  5. total cost——router判定、検索、generationを含むtoken・latency。
  6. frontier——一つのthresholdではなく、budgetを動かしたaccuracy/cost curve。

この形なら、accuracy改善が「routerが賢い」のか「検索回数を増やした」のかを分けやすい。

限界——utilityの定義がcorrectness差だけでは狭い

論文では主にcorrectnessの改善をutilityとして扱う。実サービスでは、citation quality、latency、cost、safety、coverage、answer lengthなど複数目的がある。検索で正答率が変わらなくても、根拠提示が増えるなら価値がある場合もある。

また、retrieval/no-retrievalのcounterfactualをqueryごとに評価するには両方の回答を生成する必要があり、offline evaluation costが高い。utility label自体もgenerator versionに依存する。同じdocumentでもgeneratorが変わればhelpful/harmful判定が変わり得る。

それでも「検索の価値は追加情報量ではなく介入差分で測る」という考え方は残る。何をutilityへ含めるかをdeployment目的に合わせて拡張すればよい。

実務へ持ち帰るなら

  1. 検索あり／なしを同じqueryで比較し、retrieval utility labelを作る。
  2. search triggerのscoreをutility rankingとして評価する。
  3. target retrieval rateだけでなく、held-outで実現したrateを必ず報告する。
  4. 検索で悪化したcaseをharm auditとして独立レビューする。
  5. router判定に使うLLM callやsampling costもtotal costへ入れる。
  6. 単一thresholdでmethodを決めず、複数budgetのfrontierを比較する。

「検索回数を減らした」は成果ではなく制約である。少ない検索で必要なcaseを拾い、不要・有害なcaseを避け、設定したbudgetを本番でも守るところまで測って、初めて検索制御の品質になる。

読後に考える問い

いまの検索停止条件は「何件取ったか」「何round回したか」を見ているのか、それとも「次の一回が結論・例外・根拠・coverageをどれだけ改善し得るか」を見ているのか。後者を測るなら、どんなcounterfactualを作ればよいだろうか。
