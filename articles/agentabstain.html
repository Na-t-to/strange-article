AIエージェントAI評価LLM信頼性

止まるべき時に、止まれるか——AgentAbstainで「行動しない能力」を評価する

AgentAbstain: Do LLM Agents Know When Not to Act?

Xun Liu / Yi Evie Zhang / Vira Kasprova / Parisa Rabbani / Pardis Sadat Zahraei / Tianyu Zhang / Ali Ebrahimpour-Boroojeny / Varun Chandrasekaran · 2026
公開 2026.09.24　／　推定読了 50分

AIエージェントの評価は「依頼を完遂できたか」に寄りやすい。ところが実環境では、進めること自体が失敗になる場面がある。指示が曖昧、制約同士が矛盾している、必要なツールがない、途中で証拠が食い違う、実行すると取り返しがつかない。AgentAbstainは、こうした条件で実行前または実行途中に、適切に止まれるかを独立した能力として測る。

「答えない」と「操作しない」は同じ問題ではない

質問応答でのabstentionは、分からない問いへ「分からない」と答える能力として研究されてきた。誤答を返す代わりに保留するので、最悪の失敗は不正確な文章になる。

ツールを使うAIエージェントでは事情が変わる。メールを送る、予約を取り消す、ファイルを削除する、支払いを確定する、といった操作は環境状態を変える。途中で「やはり実行すべきではなかった」と気づいても、文章上の訂正だけでは戻せない。

論文の導入例は旅行管理である。利用者が「往路をキャンセルして次便の窓側席へ取り直して」と依頼する。安全な順序は、まず次便の条件と空席を確認し、再予約可能だと分かってから既存便をキャンセルすることだ。ところが一部のエージェントは先にキャンセルし、その後で条件を満たす便がないと知る。最後に「再予約できませんでした」と正しく報告しても、元の予約は消えている。

ここで必要なのは、最終発話の正直さより不可逆な境界を越える前に判断することである。

AgentAbstainは「進む例」と「止まる例」を一対にする

AgentAbstainの中心はpaired-task designである。一つの課題について、正常に実行すべきshould-act版と、ほぼ同じだが一箇所だけ条件を変えて止まるべきshould-abstain版を作る。

課題は、利用者のquery q、状態を持つenvironment e、利用可能なtool集合 τから構成される。should-abstain版では、この三つのどれか一つへcontrolled perturbationを入れる。たとえば必須パラメータを欠かす、指示を曖昧にする、制約を矛盾させる、必要ツールを外す、環境側に食い違う証拠を置く、といった変更である。

この設計の利点は、単純な「慎重さ」を高得点にできないことにある。何でも実行するagentはshould-actでは通るがshould-abstainで落ちる。何でも拒否するagentは逆になる。論文のPaired Accuracyでは、両方を正しく処理したpairだけが成功なので、常時実行・常時拒否の固定方針は50%を超えられない。

原文外の補助例

契約レビューAIで「この条項を削除して修正版を保存して」と頼むテストだけでは、編集能力しか分からない。対になるテストとして「削除対象の条番号が二つ存在する」「保存先への書込み権限がない」「原本しかなく上書き禁止」と一条件だけ変え、そこで確認要求や停止へ切り替えられるかを見ると、実行と抑制の境界を測れる。

止まる理由は、実行前に見えるものと途中で初めて見えるものがある

benchmarkは8種類のabstention scenarioを二つのphaseへ分ける。pre-executionは、利用者の指示やtool一覧だけで停止理由が分かる。runtimeは、実際にlookupやverifyを進めて初めて問題が現れる。

Pre-execution

Missing Parameter、Ambiguous Action、Conflicting Constraints、High Stakes、Insufficient Tools。着手前のqueryやtool inventoryに停止理由がある。

Runtime

Tool Failure、Conflicting Evidence、Emergent Risk。環境を観測しながら進めた結果、当初は見えなかった停止理由が現れる。

この分割は実装にも効く。着手前のguardrailだけではruntime failureを捕まえられない。逆に、毎stepで重い安全判定を走らせても、指示段階で明らかな欠落を早期に処理できなければ無駄が多い。停止条件を「最初に一回判定するpolicy」として置くのではなく、どの情報が得られた時点で判定を更新するかとして設計する必要がある。

lookup・verify・commitを分けると、評価対象が明確になる

AgentAbstainのsandboxではtoolをlookup、verify、commitに分類する。lookupは読取り、verifyは検証用のgate、commitは環境状態を書き換える操作である。

operational taskには実行DAGがあり、そのうちstate-mutatingなcommit nodeをcritical action setとして持つ。評価はterminal responseだけでなくtool-call traceも見る。should-abstain課題で、最終文面が拒否になっていても、その前にcritical actionを実行していれば成功扱いしない。

この設計が重要なのは、自然言語だけのjudgeではpost-hoc abstentionを褒めてしまうからだ。「危険なので実行しません」と最後に書いてあっても、すでに送信や削除が済んでいれば抑制ではない。システム評価では、説明と状態遷移を別々に観測する必要がある。

既収録のAgentCheckは、同じ故障条件を再現して修正前後の回復を比較する。本稿はさらに手前で、「故障や矛盾を見たとき、回復処理へ進むべきか、そもそもcritical actionを保留すべきか」という分岐を評価対象にしている。

263 pair・42環境でも、最良のPaired Accuracyは59.5%

benchmarkは263 pair、合計526 taskを42のMCP sandboxへ実装している。環境は合計541 toolsを持ち、lookup 246、verify 119、commit 176。taskはinformational 132 pair、operational 131 pairでほぼ半分ずつである。

17のfrontier modelを4つのagent harnessで評価した結果、最良のGemini 3.1 Proでも平均Paired Accuracyは59.5%だった。13/17 modelは50%未満で、片側だけ得意な固定方針に近い振る舞いが残る。

カテゴリ差も大きい。著者らの集計では、Insufficient Toolsのようなcapability limitationは比較的見つけやすく、Conflicting Evidence、Ambiguous Action、Conflicting Constraintsのような情報・論理の問題が難しい。特にConflicting Constraintsではact側のaccuracyが高い一方、abstain側が大きく落ちる。つまり「できないから失敗する」だけでなく、実行能力はあるのに、実行してはいけない条件を区別できない。

不可逆性そのものを、モデルは十分な停止シグナルとして扱っていない

論文ではoperational taskとinformational taskも比較している。operational taskは多段tool操作が必要なためact側の難度は高い。しかしabstain accuracyは両者で大きく変わらず、拒否率もほぼ同程度だった。

著者らは、モデルが「このtool callはstateを変える」という性質を、停止判断を変える強いsignalとして扱っていないと解釈する。これはagent設計上かなり具体的な示唆になる。

commit toolを単にtool一覧の一員として渡すのではなく、不可逆性、復旧可能性、金銭・法的効果、外部公開の有無などをmetadataとして扱い、実行前にverify gateを要求する設計が考えられる。重要なのは「慎重に考えて」というpromptではなく、critical actionの前へ構造として確認点を置くことだ。

Conditioned Abstention Rateで「そもそも課題を解けない」を切り離す

abstention benchmarkには一つ罠がある。agentがshould-act側の課題自体を解けないなら、should-abstain側で止まっても「適切な判断」なのか単なる能力不足なのか分からない。

そこで論文はConditioned Abstention Rate（CAR）を使う。対応するshould-act版を正しく処理できたpairに限定し、should-abstain版でも正しく止まれた割合を見る。これによってbaseline capabilityからrestrain能力をある程度分離する。

これは評価設計一般にも使える発想である。「安全性scoreが高い」の中に、何もできないmodelを混ぜない。能力が成立する条件の中で安全側の分岐を評価する。既収録のconfidence評価がcalibrationとusefulnessを分けたのと同じく、ここでも一つの総合scoreに異なる能力を押し込めないことが重要になる。

自動生成benchmarkにも、生成物の検証工程を置いている

263 pairを手で作る代わりに、著者らはAbstainGenでsandboxとtask pairを生成する。ここでも「LLMが作ったから完成」とはしていない。DAG構造やperturbation箇所をprogrammatic validatorで確認し、別系統のLLM rubric judgeとfalsification criticを通し、should-act側は実環境でDAG replayして最後まで実行できることを確認する。

さらに100 pairのsampleを3人が独立評価し、それぞれ96%、94%、98%をwell-designedと判定した。benchmark contaminationへの対策として、新しいtask instanceを再生成できる設計も採る。

この構成は、生成AIでevaluation setを増やすときの参考になる。生成器、構造validator、反証役、実行replay、人手sample auditを別段階にすることで、「問題文がもっともらしい」だけの評価セットから離れられる。

法務・業務エージェントへ持ち込むなら「停止理由」を仕様にする

法務リサーチや契約業務では、agentの失敗を回答内容だけで定義しない方がよい。たとえば、対象会社が曖昧、準拠法が未指定、最新資料へ到達できない、二つの一次資料が矛盾する、権限がないのに外部送信を求められる、といった状態は「低confidence」より具体的な停止理由になる。

実装上は、各critical actionについて少なくとも次を持てる。

  • 実行前に必ず存在すべきparameterとevidence
  • 矛盾時に自動解消してよい範囲と、人へ返す条件
  • commit前にverifyすべき状態
  • runtimeで新しいrisk signalが出た場合の停止点
  • 停止したとき利用者へ返す不足情報と再開条件

ここでCoactive DesignのDirectabilityとも接続する。人が止められるだけでなく、agent側から「この条件では進めない。AかBを指定してほしい」と共同作業を戻せることが、実用上のabstentionになる。

この論文がまだ測っていないもの

著者ら自身、sandboxと実運用の差を大きな限界として挙げる。42環境のtoolは決定的に振る舞うが、現実のAPIは部分故障、非標準error、非同期更新を含む。結果がそのままproductionへ移るとは限らない。

8 scenarioもsingle-agent・single-turnが中心で、multi-agent delegation、長時間にわたりriskが蓄積するtask、prompt injectionは対象外である。また各model×taskは1回実行なので、確率的なばらつきを測っていない。judgeにもLLMを使うためborderline caseにはbiasが残りうる。

それでも、評価単位を「最後に正しい結果が出たか」から「いつcritical boundaryを越え、いつ停止理由を観測し、そこで行動を変えたか」へ移した点は強い。agentの信頼性は、より多くの仕事を成功させる能力だけでは完成しない。進める能力と止まる能力を、同じtask pairで同時に測るという評価設計が持ち帰れる。
