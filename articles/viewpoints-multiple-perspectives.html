要求工学仕様設計協働設計

仕様を一枚にまとめる前に、誰の見方かを分ける——ViewPointsで複数の仕様を協調させる

Viewpoints: A Framework for Integrating Multiple Perspectives in System Development

A. Finkelstein / J. Kramer / B. Nuseibeh / L. Finkelstein / M. Goedicke · 1992
公開 2026.09.21　／　推定読了 52分

大きなシステムを一枚の仕様へまとめると、誰の関心から見た記述なのかが消えやすい。性能担当は待ち時間を見る。機械担当はmotorを見る。利用者はbuttonとdoorを見る。同じ対象でも、使う表現、担当domain、検査したい関係が違う。FinkelsteinらのViewPointsは、この違いを最初から別々の仕様単位として持たせ、必要な場所で関係を張り、checkし、履歴を残すためのframeworkである。

複数視点は「意見の違い」だけではない

1992年の論文が扱うmultiple perspectives problemには、人が複数いることだけでなく、representationの違い、domain knowledgeの違い、development strategyの違いが含まれる。ある担当はPetri Netを使い、別の担当はfunctional hierarchy、さらに別の担当はaction tableを使う。同じ表現へ統一すれば解決する問題ではない。

複合システムでは、専門性ごとに適切な表現が違う。ViewPointsはheterogeneityを消す前に、どの記述がどのdomainを担当し、どのmethodで発展するかを明示する。

一つのViewPointは「仕様断片」より大きい

論文のViewPointには複数のslotがある。中心は、representation style、domain、specification、work plan、work recordである。representation styleは何の記法で書くか、domainは何について書くか、specificationは現在の記述内容を持つ。

work planは、そのspecificationをどう作り、いつどのcheckを行うかを記述する。work recordは、現在状態とそこへ至ったdevelopment historyを残す。つまりViewPointは成果物だけでなく、成果物をどう発展・検査したかまで一まとまりにする。

この構造が重要なのは、「同じ図が二枚ある」状態と「別の責任・方法で作られた二つの仕様」が区別できるからである。

liftの例では、同じシステムが別の形に見える

論文はlift systemを例にする。Kenはsystem performanceをdomainとしてPetri Netを使う。Janeはlift全体をfunctional hierarchyで記述する。Bobはschedulerをobject structureやaction tableで表す。Tomはdoorsを担当する。さらに同じmotorについて別々の人が異なるversionを持つ場合もある。

ここで一つの「lift specification」を早く作ると、どの表現を正とするかの決定が先に必要になる。ViewPointsは、domainごとの知識をそのまま保ったまま進め、重なりが生じる場所でrelationを作る。

内部の矛盾と、視点間の矛盾を分けてcheckする

Janeのfunctional hierarchyで、同名elementの追加によってdoorがdoorのpartになるような構造ができれば、これは一つのViewPoint内部のinconsistencyである。論文はin-viewpoint checkでこれを検出し、適切な時点で修正させる。

一方、JaneとTomがdoorsを独立に記述し、一方はslides、一方はbaseという要素を持つなら、二つのViewPoint間の関係が問題になる。著者らはinter-viewpoint checkを置き、重複部分に食い違いがあることを明示する。

ここで価値があるのは、仕様全体を毎回global consistencyへ戻すのではなく、どの二つの記述の、どの関係を、いつcheckするかをwork planへ持てることだ。

resolveとtransferは、同じ「整合」でも意味が違う

論文はinter-viewpoint checkの形を二つ例示する。独立して作った二つのViewPointが重なり、相違を調整する場合はresolveになる。両者に独立した知識があり、食い違いを交渉して整理する。

別のケースでは、一方が上位の記述を作り、その結果をもう一方の空のViewPointへ渡し、受け手が詳細化する。これはtransferである。同じ「情報を合わせる」でも、独立記述の衝突解決と、前提の引継ぎでは操作が違う。

この差を消すと、誰が決めた前提なのか、どこから変更できるのかが分からなくなる。仕様間relationには、データ依存だけでなく権限・責任の形も表れる。

表現が違っても、対応関係は作れる

ViewPointsは同じnotation同士だけを扱わない。Bobのaction tableに出てくるsource / destinationと、object structure diagramに出てくるobjectが対応しているかをcheckできる。さらにPetri Netのtransitionとaction tableのactionのように、異なるrepresentation style間でも部分的なrelationを置く。

実務ではこれが効く。利用規約の条項、業務フロー、DB schema、UI項目、評価datasetは同じ記法にならない。それでも「このfieldはこの法的要件を実装している」「この評価caseはこの仕様条件を検査する」というrelationは作れる。

原文外の補助例

法務AI機能を設計するとき、法務担当は「根拠がなければ断定しない」というrule、検索担当はretrieval pipeline、UX担当はcitation UI、評価担当はfailure case集を持つ。それぞれを一つの巨大文書へ混ぜるより、独立したViewPointとして持ち、「どのevaluation caseがどのruleを検査するか」「どのUI状態がどのretrieval stateを表示するか」をinter-viewpoint relationにすると、変更の影響範囲を追いやすい。

ViewPoint templateは「方法」と「案件」を分ける

同じstyleとwork planを複数のViewPointで再利用するため、著者らはViewPoint templateを導入する。templateはspecification、domain、work recordが空で、representation styleとwork planを持つ。案件固有の内容を入れる前の「作り方の型」である。

同じnotationを使っていてもdevelopment strategyが違えば同じtemplateではない、という点も細かい。同じ形式の表を使うことと、同じmethodで設計していることは別だからである。

work recordは変更履歴以上のものになる

work recordは、現在のspecification stateと、work planに沿ってどのactionを実行したかのhistoryを持つ。論文はこれをcurrent stateのrationaleとして位置づける。

Gitの差分だけでは、「なぜこのcheckをしたか」「どのViewPointとの矛盾を解いたか」「どの情報をtransferしたか」は十分残らない。ViewPointsではdevelopment actionが方法の一部として定義され、その実行履歴が残るため、変更理由を追いやすい。

Requirements Traceabilityが要求の由来と下流への連鎖を追うなら、ViewPointsは並行する複数の記述と、その間の整合・転送操作へ焦点を当てる。

不整合は「即座に全部消す」より、場所と時点を管理する

1992年論文のframeworkは、in-viewpoint checkを終えてからinter-viewpoint actionを行うなど、局所的なconsistency ruleを持つ。したがって「矛盾を放置してよい」という主張ではない。

ただし発想として重要なのは、開発中のすべての記述を常時一つのconsistent modelへ強制しないことだ。各ViewPointが独立に発展し、必要なoverlapについてcheckを定義する。後続研究では、この考えが「完全整合を常時維持する必要はない」というinconsistency managementへ発展した。

要求探索中の食い違いは、誤記だけではなく未決定事項を示すことがある。先に片方へ統一すると、誰の前提が消えたか分からなくなる。

Twin Peaksとの違い——往復する対象をさらに複数化する

Twin Peaksはrequirementsとarchitectureを並行に具体化する。ViewPointsは、その内部にさらに複数のowner、domain、representation、methodがあると考える。

両方を合わせると、「要求担当と設計担当が往復する」だけでは足りず、どのViewPointの何が変わり、どのrelationを再checkするかまで設計できる。変更通知を全員へ飛ばすのではなく、依存するcheckを再実行する形へ近づく。

限界——分ければ自然に協調できるわけではない

ViewPointsはconflictそのものを解く政治的・組織的手続きを自動で与えない。二人の専門家が異なる要求を持つとき、どちらを優先するかはframework外の判断になる。またViewPoint、relation、work planを細かく定義するほど管理コストは増える。

論文のtool prototypeやnotationは1990年代のCASE環境を前提にしている。現在の実務へ移すなら、専用toolを再現する必要はない。Git、issue、schema、test、decision logを使いながら、ViewPointの境界とcross-checkを明示する方が現実的である。

設計に持ち帰るなら

巨大な仕様書を作る前に、少なくとも「owner / domain / representation / current specification / check rule / work history」を分けてみる。次にViewPoint間で重なるconceptを列挙し、何が一致すべきか、何は独立に違ってよいか、どの変更で再checkが必要かを決める。

AI開発なら、prompt、retrieval policy、evaluation set、UI、法務ruleを別ViewPointとして扱える。重要なのは一つの正規文書へ急いで統合することより、異なる記述の間に検証可能なrelationを作ることである。
