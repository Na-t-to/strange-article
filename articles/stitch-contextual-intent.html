似ている記憶より、今の目的に合う記憶を取る——STITCHでAgent Memoryを文脈化する

Grounding Agent Memory in Contextual Intent

Ruozhen Yang / Yucheng Jiang / Yueqi Jiang / Priyanka Kargupta / Yunyi Zhang / Jiawei Han · 2026
公開 2026.09.19　／　推定読了 41分

長期対話の記憶検索で厄介なのは、過去を忘れることだけではない。よく似ているが、今とは別の目的で出てきた情報を思い出してしまうことがある。旅行計画で同じホテル名がDay 1とDay 2に現れ、価格も複数回更新されたなら、「Apollo Hotelの価格」というsemantic similarityだけでは正しい記憶を選べない。STITCHは各履歴へ、現在のテーマ、行為の種類、重要なentity typeを構造化したcontextual intentを付ける。検索時には意味の近さだけでなく、その構造が現在の目的と適合するかを先に見る。

長期memoryの問題を「保存容量」から「取り違え」へずらす

agent memoryの研究では、長い履歴をどう圧縮するか、context windowを越えた情報をどう保存するかが中心になりやすい。STITCHの出発点は少し違う。履歴を保存できても、同じentityや似た事実が別々のgoalの下で繰り返されると、retrievalが文脈違いの証拠を返す。

たとえば旅行agentが三日間の旅を組む途中で、同じホテルを複数日について検討する。Day 1では245ドル、Day 2では別価格、途中で予約方針も変わる。「そのホテルはいくらだった？」という問い合わせに対し、embeddingはどの価格も高い類似度を付けうる。必要なのは単語の近さではなく、どの日の計画、どの行為、どの属性について問われているかである。

著者らはこれをcontextual interferenceとして扱う。memory unitの内容自体は正しくても、現在のgoalと違う履歴が混ざれば最終回答は誤る。

STITCHが持つ三つのretrieval cue

STITCHは、trajectoryの各stepへcontextual intent tupleを付ける。構成要素は三つある。thematic scope、event type、key entity typesである。

thematic scopeは、そのstepが属する現在のgoal segmentを表す。論文の旅行例なら「Day-1 plan」のようなまとまりである。同じhotel bookingでも、どの旅程部分を進めているかを分ける。

event typeは、そのstepで何をしているかを表す。searching、comparing、bookingのように、特定のsegmentを越えて再利用できる行為の型である。STITCHは固定taxonomyを事前に与えず、履歴から動的にlabelを作る。

key entity typesは、現在のgoal達成に必要な属性の種類である。Hotel、Price、Ratingのような型が、どの細部を表面へ出すべきかを支える。固有名詞そのものだけでなく、何の属性として扱っているかを残す。

「Day 1のホテル予約で見た価格」までmemoryへ埋め込む

論文のFigure 2では、「Book it at price $245 for that day」のように、単体では参照先が曖昧なstepを扱う。STITCHは周辺履歴と構造labelを使ってcoreferenceを解き、「Day 1のApollo Hotelを245ドルで予約する」といったcanonicalなcontentへ解消する。

その上でraw step、contextual intent、canonical summaryを一つのMemory Snippetとして保存する。つまりmemoryは文章断片だけでなく、その文章がどの目的のどの操作として生まれたかを一緒に持つ。

これは単なるmetadata付与より一歩踏み込む。metadataがretrieval時のfilterとして実際に使われ、semantic rankingの前に検索空間を狭めるからである。

検索時は「構造が合うもの」を先にし、その後で意味類似を見る

queryを受けたSTITCHは、query側についてもtargetとなるscope・event・entity typeのfilter configurationを推定する。次にmemory snippetがいくつのlabel条件へ一致するかを使って優先順位を付ける。著者らはこれをLabel Density Rankingと呼ぶ。

構造上の一致度が同じmemory同士で初めてsemantic similarityを使う。つまりembedding similarityを捨てるのではない。意味の近さへ入る前に、現在の目的と整合する候補集合を作る。

この順序が重要である。「Apollo Hotel」「price」という語が完全一致しても、Day 2のbooking memoryならDay 1の質問には低く扱う。逆に、表現が少し違っていても同じscopeとeventに属すれば候補として残りやすい。

CAME-Benchは、似た事実を意図的に混ぜてmemoryを試す

著者らはCAME-Benchというbenchmarkも作る。目的は、長いgoal-oriented trajectoryの中で、繰り返しentityやinterleaved goalsがあるときに正しいcontextを取れるかを見ることにある。

trajectoryは旅行計画やdebateなど複数domainを持ち、単純なturn-takingや話題ごとの完全分離に寄らない。question typeも、state update、context-aware factual recall、multi-hop reasoning、information synthesisへ分かれる。長さについてSmall、Medium、Largeを置き、contextが増えたときの劣化を見る。

このbenchmark設計自体に価値がある。memory systemを「昔の事実を覚えていたか」だけで評価すると、near-duplicateな情報の選別能力が見えない。正しい記憶が保存されているのに、別goalの記憶を取る失敗を独立して測る必要がある。

長くなるほど、構造化したintentの差が出る

CAME-BenchでSTITCHはSmallのMacro-F1 0.844、Medium 0.682、Large 0.592だった。long-context modelやembedding RAG、structured-memory baselineは、履歴が長くなるとより大きく崩れる。論文全体ではCAME-BenchとLongMemEvalで強いbaselineを最大35.6%上回ったと報告する。

一方、Smallではlong-context modelも競争力がある。履歴が短く、似た情報の干渉が少ないなら、複雑なmemory structureの価値は小さくなる。STITCHの利点は「どんな会話でも常に構造化が勝つ」ではなく、長期化・反復・goalの交差によってsemantic similarityだけでは区別しにくくなる場面で強く出る。

Lost in the Middleが、必要情報がcontext内に存在しても位置によって利用性能が変わることを示したのに対し、STITCHはcontextを外部memoryへ移した後のretrieval interferenceを扱う。

ablationではthematic scopeが特に大きい

構成要素を外すablationも分かりやすい。Large subsetのMacro-F1はfull STITCHで0.592。thematic scopeを外すと0.213、event typeを外すと0.273、key entity typeを外すと0.458、coreference処理を外すと0.404へ下がる。

少なくともCAME-Benchでは、「何について話しているか」というgoal segmentの境界が大きな役割を持つ。単語やentityの種類を増やすだけでは、似た話題が何度も出る履歴を分けきれない。

ここはコンテキストは相互作用の途中で作られると並べると面白い。Dourishはcontextを固定属性の袋として考える危険を指摘した。STITCHは別の立場から、goalの移り変わりを履歴中で動的にsegmentし、retrieval cueとして使う。両者を同一視はできないが、「現在の意味は属性の単純一致だけでは決まらない」という問題意識は接続する。

粒度が粗すぎても、細かすぎても壊れる

STITCHの興味深い限界は、contextを構造化すれば終わりではない点にある。thematic scopeのwindowを大きくしすぎると、別episodeが同じsegmentへ入り、near-duplicate factを区別しにくくなる。反対に小さすぎるとtrajectoryが細切れになり、turnをまたぐcoreferenceやmulti-hop reasoningが壊れる。

論文のstress testでは、defaultを50 turnsとし、10 turnsのover-segmentationと100 turnsのunder-segmentationを比較する。大きすぎるwindowはcontext-aware factual recallを特に傷つけ、小さすぎるwindowはmulti-hop reasoningをより傷つけた。

これはmemory schemaの粒度を設計変数として扱う理由になる。「細かくタグ付けするほど良い」ではない。検索時に必要な区別を保ちつつ、推論に必要な連続性を切らない粒度が要る。

event typeも、細かすぎるとsynthesisを邪魔する

event taxonomyにも同じtrade-offがある。Check RatesとBook Hotelのような細かいevent typeは特定のlookupには効く。しかし、「この旅で検討した宿泊候補をまとめて」のようなsynthesisでは、複数eventを横断して集約する必要がある。

著者らはflat taxonomyではこの両立が難しく、hierarchical structureが将来課題になると述べる。特定事実検索と広域要約を同じmemory indexで支えるなら、細粒度labelと上位概念の両方が必要になる。

Formal Ontologyで扱ったtype / roleや階層設計とは目的が違うが、label granularityが後続操作を左右するという点では接続できる。

query側のintent推定を間違えると、正しいmemoryを消してしまう

STITCHのfilterは強力だが、filter条件そのものを間違えると危険である。error analysisでは、questionから導けないlabelをもっともらしく選んでしまうNon-Inducible Labelが78.4%、抽象度が粗すぎる・細かすぎるGranularity Mismatchが71.8%のjudged casesで観測された。複数failureが同一caseへ付くため合計は100%を超える。

強いfilterは、noiseを減らす一方でrelevant evidenceを検索前に落とせる。したがってcontextual intentは「正解ラベル」として扱うより、retrieval priorとして扱う方が安全である。著者ら自身も、hierarchical labelやquery時のrefinementを今後の方向として挙げる。

ingestion時に計算し、query時のコストを下げる

STITCHは履歴が来るたびにLLMを使ってscope・event・entity type・summaryを作るため、embeddingだけを保存する方式よりingestion costが高い。論文はこのコストを明示的なtrade-offとして扱う。

一方、query時には構造filterで探索範囲を絞れるため、強いstructured-memory baselineより少ないquery tokenで済む設定がある。長期運用するagentなら、保存時に多く計算して検索時を軽くする設計が合理的な場合がある。

これはRAGのindexingでも同じである。document ingestion時に法域、資料種別、時点、対象制度、条文参照などを高品質に付ければ、query時の探索を狭められる。ただしmetadata生成誤りが長期間残るので、修正可能性も必要になる。

法務・調査agentへ持ち込むなら「同じ法令名」を区別する

長期の法務調査でも、同じ法令・同じ会社名・同じ契約類型が別案件、別時点、別論点で何度も出る。semantic similarityだけでmemoryを取ると、前案件の結論や古い時点の前提が混ざりやすい。

原文外の補助例

あるagentが数週間にわたり「個人情報保護法」について複数案件を扱うとする。今は委託先監督を調べているのに、過去の越境移転案件のメモが「個人情報保護法」「第三者」「提供」という語の近さで上位に来るかもしれない。案件scope、調査行為、必要entity typeを分けて持てば、同じ法令名でも現在の調査へ必要なmemoryを優先しやすい。

ここで重要なのは、STITCHの三要素をそのまま法務へコピーすることではない。どのcontextual cueが実際に誤検索を減らすかをdomainごとに検証する必要がある。案件、法域、時点、論点、資料種別、task stageなど候補は多い。

限界——synthetic benchmarkとLLM-generated schemaの上に立つ

CAME-Benchはclosed-worldのsynthetic benchmarkで、Travel PlanningとDebateを中心に作られている。個人データを避けられ、干渉条件を制御しやすい利点がある一方、現実の企業agentが持つ権限変更、組織語彙、誤記録、削除要求、長期の制度変更まで再現しているわけではない。

またSTITCHはcontextual intent構築そのものに複数のLLM callを使う。間違ったsegmentやlabelが保存される可能性があり、buffered updateは新しいevent typeの反映に遅延を生む。細粒度taxonomyはbroad synthesisを苦手にする。著者らはこれらをlimitationsとして明記する。

したがって「embedding検索を構造filterへ置き換えれば解決」と読むより、memory retrievalには意味類似以外の変数が必要で、その変数にも誤り・粒度・更新コストがある、と読む方が実務的である。

設計に持ち帰るなら

長期memoryの評価datasetを作るとき、同じentity・似た事実を異なるgoalで意図的に再登場させる。正しい記憶が保存されているかだけでなく、現在のgoalと違う記憶を拾わないかを見る。retrieval logにはsemantic scoreだけでなく、scopeやtask stageなどの構造一致も残す。

そしてlabel設計そのものを評価対象にする。scopeの境界は適切か。細かすぎるevent typeがsynthesisを阻害していないか。queryから推測できないlabelで先にfilterしていないか。memory品質は「何を覚えるか」と同じくらい、「何を思い出す条件にするか」で決まる。
